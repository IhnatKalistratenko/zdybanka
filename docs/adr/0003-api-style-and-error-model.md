# Architecture Style — Модульний моноліт

## Контекст

Проєкт розробляється однією людиною, яка відповідає за розробку backend та frontend частин застосунку, а також за його розгортання та деплой.

Процеси розробки та експлуатації застосунку виконуються однією людиною, тому архітектура має бути достатньо простою для розробки, тестування, розгортання та подальшого супроводу.

На поточному етапі проєкт не потребує незалежного масштабування окремих частин системи або розподіленої інфраструктури.

## Рішення

Застосунок буде розроблятися у вигляді **модульного моноліту**.

Кожен модуль відповідатиме за окрему функціональну область застосунку. Модулі повинні мати чітко визначені межі та взаємодіяти між собою через визначені інтерфейси.

Фізично застосунок розгортатиметься як єдина система, але внутрішня структура буде організована таким чином, щоб функціональні модулі залишалися максимально незалежними один від одного.

## Альтернативи

### Мікросервісна архітектура

Цей підхід не обрано через додаткову складність розробки, розгортання, моніторингу та підтримки декількох незалежних сервісів для проєкту, який розробляється однією людиною.

### Моноліт без модульного поділу

Цей підхід спрощує початкову реалізацію, але ускладнює підтримку та подальший розвиток системи через сильнішу зв'язаність компонентів.

## Наслідки

### Позитивні

* **Простота розгортання** — застосунок розгортається як єдина система, без необхідності координувати декілька незалежних сервісів.
* **Простота розробки** — відсутня необхідність підтримувати складну міжсервісну взаємодію, окремі пайплайни та інфраструктуру для кожного сервісу.
* **Чітке розділення функціоналу** — модульний поділ дозволяє локалізувати логіку окремих функціональних областей та зменшити зв'язаність компонентів.

### Негативні

* **Деградація архітектури** — без дотримання визначених меж модулі можуть поступово ставати сильно пов'язаними між собою, перетворюючи модульний моноліт на складний моноліт.
* **Спільні ресурси** — модулі використовують спільний процес виконання та інфраструктурні ресурси, що зменшує їхню незалежність.
* **Обмежене масштабування** — окремі модулі не можуть незалежно масштабуватися як окремі сервіси.
* **Єдиний реліз** — зміни в окремому модулі потребують розгортання всієї системи.
